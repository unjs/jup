# 10 — Shims & PATH Integration

`enable` puts jup's names on `PATH`; `disable` takes them off. Everything
elsewhere assumes `enable` has run, or that the user types `jup <name>`
explicitly. `src/commands/shims.ts` is the implementation;
`test/unit/shims.test.ts` asserts the generated bytes.

## 10.1 What a shim is

A shim for binary `B` invokes jup as if the user had typed `jup B <args…>`, with
the download-prompt default at `1` (§05.4) — the user asked for `B`, not for a
download.

On POSIX, each name is a symlink to **its own stub**, `<B>.mjs`, which resolves
the jup entry point from its own realpath and runs the name written into it. On
Windows, wrappers name the binary explicitly for the same reason: the runtime
does not receive the wrapper's invocation name. Every stub and wrapper is mode
`0755` and carries the shim marker (`@jup-shim`) that §10.6's ownership test
looks for — except the Windows wrappers, whose bodies are byte-exact, and which
are recognised by their exact generated contents instead.

jup's own two names are not stubs at all: §10.9 points them straight at the CLI
entry, which defaults the prompt to `0` and passes argv through unchanged.

**The name is written into the stub; a stub must never derive it from `argv[1]`.**
One stub reading `basename(argv[1])` would serve every name and is correct under
node, which leaves `argv[1]` as the path the user invoked — but **bun replaces it
with the script's realpath**, so such a stub would read its own filename as the
name it was asked to run. The kernel passes the invoked path, but by the time the
stub runs there is no portable way back to it. A stale link is corrected by
`enable` rewriting it, not by there being a single file to point at.

## 10.2 Pinning the interpreter

Wherever a shim names the interpreter as a bare `node`, that name must instead be
an **absolute path**: the `realpath` of a suitable runtime, resolved at `enable`
time. A bare name is unsafe because `cmd.exe` searches the current directory and
`#!/usr/bin/env node` re-searches `PATH` — and if the shim directory claims
`node`, either lookup recurses into the shim. `realpath`, because
`process.execPath` is frequently a symlink into a version manager's store, and
the point of baking a path in is that it names one file.

**When it applies.** Windows wrappers always bake it in. POSIX bakes it into the
stub's shebang under either condition:

1. The install directory claims the interpreter's own name — this run enables
   `node`, or an earlier one already installed a shim of ours at that name. A
   *foreign* `node` there does not count.
2. `PATH` holds no `node` at all that is not a shim of ours. A generic shebang is
   then not a recursion but a dead file: the kernel finds no interpreter and the
   shim exits 127. This is the machine an install script bootstraps, whose
   runtime sits beside the store rather than on `PATH`.

Otherwise the stub keeps `#!/usr/bin/env node`, so shipped stubs stay relocatable
and a read-only stub folder is not rewritten for a user who never asked for a
`node` shim.

The same condition governs **jup's own CLI entry** on every platform — the file
`package.json`'s `bin` names, which need not sit in the stub folder. When pinning
is required, read the entry and replace only its first line, writing a temp file
in the entry's own directory, preserving its mode, and renaming over it. If there
is no built entry, do nothing: a source checkout is not an installation, and
pinning one would leave an absolute shebang in a tracked file. On `EROFS`,
`EACCES` or `EPERM`, fail **before writing any shims** and name the entry and the
remedies. `disable` never restores the old shebang.

**Which runtime.** Once `enable node` has claimed `node` on a prepended shim
directory, jup's own entry point resolves through that shim and may end up
running under a runtime inside the **install folder**, which `cache clean`
exists to delete. Never bake in such a runtime. Select, in order:

1. `realpath(process.execPath)`, when it is **not** inside the install folder;
2. `JUP_HOST_RUNTIME` (§08.3), when it names an executable file that is neither
   inside the install folder nor a shim of ours;
3. the first `node` on `PATH` that is neither, resolved through `realpath`.

If none yields a runtime, `enable` **fails and writes nothing**, naming what it
found, naming `<home>`, and saying that baking it in would break every shim at
the next `cache clean`. It must not fall back to `#!/usr/bin/env node`, which is
the exec loop above, and must not bake the store path.

**The boundary is the install folder, not `<home>`.** The question is "would
`cache clean` take this runtime away", and §07.11 puts `self/` — and anything an
installer parks beside it, such as `<home>/node` — outside `v1` precisely so a
clean cannot reach them. Such a runtime is as durable as one installed by hand
and must be nameable; refusing it is what leaves a bootstrapped machine holding
shims that resolve to nothing. The test is a path-boundary test on resolved
paths, not a string prefix: `~/.cache/jup/v1` does not contain `~/.cache/jup/v10`.

> This is the most intricate mechanism in jup, and it reaches into three other
> places: §07.9 reads shebangs back out of the shims to know what `cache clean`
> may delete, §08.3 forwards `JUP_HOST_RUNTIME` through native children, and
> §10.8 turns two of its failures into `enable` errors.
>
> **Moving the pin into a state file every stub reads does not work, and is not a
> debt to pay down.** A POSIX shim's *shebang* is what the kernel executes;
> nothing runs before it that could read a state file. Making it work means
> turning each shim into `#!/bin/sh` plus `exec "$(…)" stub "$@"`, which adds a
> shell fork to every single `yarn` invocation — against §01.3's warm-path
> budget, the property jup is built to have. The choice here is binary: keep
> `enable node` and accept this mechanism, or drop the feature. It is kept, so
> the intricacy above is the intrinsic price of putting `node` on `PATH` beside
> nvm, not a design awaiting cleanup.

## 10.3 POSIX shim creation

```
file   := installDirectory/binName
target := RELATIVE path from installDirectory to stubFolder/<binName>.mjs
st     := lstat(file)                      # lstat, NOT stat

st exists:
    symlink?
        Yarn Switch target        → warn, skip, exit 0
        readlink === target       → already correct, return without writing
    not jup-owned and no --force  → print the foreign-entry message, return
    not jup-owned                 → back it up and record it before replacing
    unlink(file)
symlink(target, file)
```

Required properties:

1. **`lstat`, not `stat`** — a dangling symlink must be detected as a symlink,
   not as a missing file.
2. **The link target is relative**, so the tree stays relocatable. This is why
   the install directory is `realpath`'d first (§10.5): a relative path computed
   from a symlinked directory would be wrong.
3. **Idempotent.** An already-correct symlink is not rewritten and its mtime does
   not change across repeated `enable` runs.
4. **A stub is written only when it is not already current**, so `enable`
   succeeds against a read-only stub folder that shipped every stub — which is
   the ordinary install, since the published package carries one stub per table
   binary.
5. **The stub is executable when `enable` returns.** A symlink carries no mode of
   its own, so the bit the kernel checks is the stub's, and a shim pointing at a
   non-executable stub is skipped by `PATH` lookup without a word. `enable` tests
   the stub and `chmod`s it `0755` **only** when it is not executable, so
   property 4 still holds for the warm run.

### Yarn Switch

Yarn Switch installs a `yarn` whose realpath contains `…/switch/bin/…`. Both
`enable` and `disable` refuse to touch such an entry, warn, and exit 0. The check
applies to any name containing `yarn`, so `yarnpkg` too. POSIX only; on Windows
the check is not performed and `disable` removes the files.

## 10.4 Windows shim creation

Windows has no usable symlink story here (it needs elevation or developer mode),
so three wrappers are written per name:

| File | For |
|---|---|
| `<B>` (no extension) | sh — Git Bash / MSYS / Cygwin |
| `<B>.cmd` | cmd.exe |
| `<B>.ps1` | PowerShell |

All three are created unconditionally — the generator can be invoked from a POSIX
build machine — at mode `0755`, and overwritten unconditionally; there is no
idempotency short-circuit on Windows.

Each wrapper prefers `%~dp0\node.exe` / `$basedir/node` when the shim directory
*is* the Node install directory (which keeps that arrangement relocatable) and
otherwise names the baked-in absolute interpreter (§10.2). The `.cmd` wrapper
strips `.JS` from `PATHEXT` so that `node` resolves to `node.exe` rather than
recursing into a `node.js` file; the `.ps1` wrapper forwards pipeline input and
propagates `$LASTEXITCODE`.

**Each existing entry is removed before its replacement is written, never written
through.** Ownership and `--force` decide whether the name may be taken, so what
reaches the write is one of ours — possibly a symlink left by an earlier
POSIX-style `enable`, or one pointing at a stub folder that no longer exists. A
write that follows the link edits the link's target instead of replacing the
shim, and fails with `ENOENT` when that target is gone.

The exact wrapper bodies live in `src/commands/shims.ts` and are asserted
byte-for-byte by the unit test, because ownership detection matches on them.

## 10.5 Install directory resolution

`--install-directory` wins. `--system` is mutually exclusive and selects
`/usr/local/bin`, or `%ProgramData%\jup\bin` on Windows. Otherwise
`JUP_SHIM_DIRECTORY`, else a **closed list** of candidates:

* Linux/BSD: default `$XDG_BIN_HOME` when absolute, else `<home>/.local/bin`;
  alternates `$XDG_BIN_HOME`, `<home>/.local/bin`, `<home>/bin`.
* macOS: default `<home>/.local/bin`; same alternates.
* Windows: `%LOCALAPPDATA%\jup\bin`, no alternate.
* For uid 0 only, the system directory is appended **last** — a per-user
  directory already on `PATH` is still the better answer for root, and for anyone
  else the ownership gate would reject it. It is a candidate rather than a branch
  so that `disable` and `info` can find shims installed that way.

Nothing on this list comes from `PATH`; `PATH` only decides *among* these, and
only for `enable`:

```
the default, if it is on PATH
else the first candidate that already contains a jup-owned shim
else the first eligible alternate that is on PATH
else the default
```

A directory is never adopted merely because it is writable and on `PATH`. Every
existing directory selected automatically must be owned by the effective user, be
neither group- nor world-writable, and pass a writability probe. An alternate's
matching `PATH` entry must be absolute and the directory must already exist.
Explicit `--install-directory` and `--system` skip the ownership and mode gate
but still probe for writability, and never fall back.

Only the default is created, explicitly at mode `0755` independent of umask, and
then `realpath`'d. A bare `enable` that cannot write its initial selection falls
back to the default and says so. Alternate selection and writability fallback each
print their own `!` line. When the chosen directory is not on `PATH`, `enable`
says so and prints the export line for the user's shell.

For `disable`, `info`, and child `PATH` promotion, prefer the candidate that
already contains a jup-owned shim, without consulting `PATH`.

## 10.6 Ownership, displacement and `disable`

Before replacing an entry, `enable` must establish that it is jup's. A POSIX
entry is owned only when it points at a file of ours — a stub carrying the shim
marker, or (for jup's own two names) the CLI entry, which carries it too. A
dangling link is owned when it still names `<binName>.mjs` or the CLI entry. A
Windows entry is owned only when its complete generated contents, or its native
executable identity, match. **A name or file extension alone is never proof of
ownership.**

Without `--force`, a foreign entry is left unchanged and reported:
`<binName> already exists at <file> and was not installed by this tool -
skipping (use --force to overwrite)`.

With `--force`, every displaced entry is moved to `<home>/displaced/` and its
path, type, mode, backup path and symlink target recorded in `<home>/shims.json`
**before** the shim is installed. Existing unresolved records are never
overwritten. If installing a shim fails after displacement, `enable` rolls the
displaced entry back before returning the error.

`disable` applies the same ownership test per platform entry and removes only a
jup-owned one; a missing or foreign entry is left alone. After removing an owned
entry — or when the destination is already absent — it **restores** the displaced
entry from `shims.json`, type, contents or link target and mode included, then
atomically clears that record and backup. It never restores over a foreign entry
installed after jup's shim, and a failed restoration is reported by path with the
record retained for another attempt.

`disable` never touches a name it was not asked about and is safe to repeat.
`disable yarn` covers `yarn` and `yarnpkg`, because a name expands to its full
binary set.

## 10.7 Target set

With no names, `enable` covers every entry except those with `shimByDefault:
false`; npm is included, and `--exclude <name>` opts a name out. `disable` with
no names covers **every** entry, opt-outs included: removal has no such hazard,
and a `disable` that declined to undo an `enable bun` would be the surprising one.

Each name expands to every binary it declares across all bands, deduped (§02.5).
All binaries are processed concurrently. `info` reports every binary name
regardless of the default set.

### Living beside a version manager

`enable node` claims `node` on `PATH`, and on many machines something else
already has it — nvm being the common case. There is no arbitration and none is
needed: whichever shim directory comes first on `PATH` wins, and nvm re-prepends
its own on every shell start and `nvm use`. This is why a runtime is never in the
default set: the collision exists only for someone who typed `jup enable node`,
which is a deliberate act with a predictable outcome. The matching rule is that
jup *reads* `.nvmrc` and leaves everything else alone — no shell hooks, no
profile writes, and it never removes or shadows another tool's directory.

## 10.8 Read-only installations

A read-only directory *holding jup itself* is the common case — a global npm
install, a container image, an OS package — and `enable` succeeds there, because
§10.3 property 4 compares the stub before rewriting it and the shipped stub is
already current.

Three things break that truce, and each fails rather than warns, because in each
the shims about to be written could not work. All three name the specific file
and its own remedy:

* shimming the runtime rewrites the **stub** to pin the interpreter (§10.2), and
  the remedies do not move that file;
* shimming the runtime also rewrites **jup's own CLI entry**, for the same reason;
* the stub is current but not executable and the required `chmod` is refused.

When the shim **directory** is unwritable, the error names the two real options:
`--install-directory <a writable dir on PATH>`, or shell aliases.

## 10.9 Self-install shims

`self-install` (§09.12) claims jup's **own** names — `jup` and `corepack`, the two
keys of the package's `bin` — pointing them at the copy in `<home>/self/<version>`.
How a name is claimed is §10.3 and §10.4 unchanged: ownership, `--force`,
displacement, the idempotent no-write, the directory chain, the `PATH`
verification. Only the target differs, and both platforms name the same file: a
relative symlink to the CLI entry on POSIX, §10.4's trio naming it on Windows.

Three consequences:

1. **Neither name may be given a stub of its own.** A stub for `jup` would be
   `jup.mjs`, which is the CLI entry's own name, and writing it would destroy the
   entry. Pointing at the entry is also what these names want: the download
   prompt defaults to `0` rather than `1`, and argv passes through unchanged
   rather than gaining a leading binary name — without which `jup use pnpm@12`
   arrives as `["jup", "use", …]` and is rejected as an unknown command.
2. **The CLI entry carries the shim marker**, because it is the target the
   ownership test resolves to; without it `disable` would leave both names on
   `PATH`.
3. **A copy the running version did not produce is linked as it arrived.**
   `self-upgrade` installs a *different* version, whose CLI entry belongs to it;
   regenerating that file from the running version's source would put an old
   entry in front of a new bundle. The only byte that may change is the shebang
   of §10.2, under its condition.
