# Corepack

> jup keeps Corepack's familiar workflow, then makes it safer, more reproducible, and useful for more tools.

Already using an exact `packageManager` pin for npm, pnpm, or Yarn? You can usually switch to jup without changing `package.json`:

```sh
jup enable
pnpm install
```

The `pnpm`, `yarn`, and `npm` commands still work normally. jup reads the project pin, downloads the requested version, verifies it, caches it, and runs it.

::note
One exception: a **pnpm 12 or later** pin carrying a digest, such as `"pnpm@12.1.2+sha512.abc123..."`. pnpm is a native binary from 12 on, published as one file per operating system and architecture, and jup installs your system's file rather than the wrapper package Corepack downloads — so a digest written by Corepack describes bytes jup never fetches, and the run stops with a hash mismatch. Run `jup use pnpm@12.1.2` once to rewrite the pin without a digest; jup verifies each system's own download against the registry's signature instead. See [Projects](./projects#pin-a-manager-with-per-system-builds).
::

## Why use jup?

| Benefit | Corepack | jup |
| --- | --- | --- |
| 📦 Package managers | npm, pnpm, Yarn | ✅ npm, pnpm, Yarn, aube, Bun, Deno, and nub |
| 🟢 Node.js versions | ❌ Not managed | ✅ Can pin and run Node.js too |
| 🔒 Reproducible ranges | ⚠️ Exact pins only | ✅ Ranges such as `pnpm@^9` can be locked in `jup.lock` |
| 🛡️ Download safety | Basic registry verification | ✅ Project digests, signatures, safer registry checks, and clear warnings |
| 🌐 Proxies and mirrors | ⚠️ Depends mostly on Node behavior | ✅ Built-in proxy, retry, `.npmrc`, and per-tool mirror support |
| 🧩 Existing commands | ⚠️ May overwrite them | ✅ Leaves them alone unless you use `--force`, then restores them on disable |
| 🔍 Troubleshooting | ⚠️ Limited visibility | ✅ `jup info` explains the project, selected version, cache, and shims |
| ⚡ Startup and size | ⚠️ ~23 ms added per run, 520 kB loaded | ✅ ~8 ms added per run, 52 kB loaded |

## Faster and smaller

On a cached run, both tools read the project version, check the cache, and start the tool. jup loads less JavaScript to do this.

| Measure | Corepack | jup |
| --- | --- | --- |
| JavaScript loaded | 520 kB (105 kB gzipped) | 52 kB (17 kB gzipped) |
| Package size | 521 kB | 205 kB |
| Time added to a cached run | ~23 ms | ~8 ms |
| Total time for cached `npm --version` | ~49 ms | ~33 ms |

::note
These results come from `pnpm bench` on Node.js 24 for Linux x64. Both tools used the same pinned and cached package manager with the network disabled. Results vary by machine.
::

## More tools supported

Corepack focuses on npm, pnpm, and Yarn. jup uses the same workflow for:

- npm, pnpm, Yarn, and aube;
- Bun, Deno, and nub; and
- Node.js itself.

For example:

```sh
jup use pnpm@10
jup node@22 script.js
```

Package managers are pinned through `packageManager`. Node.js is pinned through `devEngines.runtime`, with `.nvmrc` supported as a fallback.

npm, pnpm, Yarn, and aube shims are enabled by default. Enable runtime-style tools explicitly:

```sh
jup enable bun deno nub node
```

::warning
`jup enable node` puts jup's `node` command ahead of your existing Node.js installation. Only enable it if you want project-selected Node versions everywhere.
::

## Reproducible ranges and tags

An exact pin is always reproducible:

```json
{
  "packageManager": "pnpm@9.15.9"
}
```

jup also lets a project keep a convenient range or tag in `package.json`:

```json
{
  "packageManager": "pnpm@^9"
}
```

Run `jup use pnpm@^9` to set and resolve it, or `jup up` to refresh an existing resolution. jup records the selected version and digest in `jup.lock`:

```json
{
  "version": 1,
  "resolutions": {
    "pnpm@^9": {
      "resolved": "9.15.9",
      "integrity": "sha512-..."
    }
  }
}
```

Commit both files. Developers and CI will then use `9.15.9` instead of independently selecting whatever release is newest that day. Run `jup up` again when you want to update to a newer matching release.

## Safer downloads and configuration

jup closes several unsafe or surprising Corepack behaviors:

- it verifies downloads using a project digest, a registry signature, or a registry digest;
- it validates download URLs and keeps credentials scoped to the correct registry;
- project env files cannot disable verification or inject credentials;
- project `.npmrc` files cannot provide credentials or weaken TLS;
- it verifies single-file tool downloads as well as full archives; and
- it handles expired signing keys without silently accepting tampered files.

See [Security](./security) for the trust model and policy settings.

## Better support for real networks

jup directly supports common development and CI setups:

- `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, and `NO_PROXY`;
- automatic retries for temporary network failures;
- a safe subset of `.npmrc` registry and authentication settings;
- custom certificate authorities; and
- a separate mirror for each managed tool through `JUP_REGISTRY_<NAME>`.

This avoids relying on hidden Node flags just to use a corporate proxy. See [Registry](./registry).

## Shims that do not destroy existing commands

Corepack may replace a command that already exists. jup refuses to overwrite a foreign file unless you explicitly pass `--force`:

```sh
jup enable --force
```

When jup does replace a command, it records the old one. `jup disable` can then restore it.

jup manages npm by default so it can reject `npm install` when a project is pinned to pnpm or Yarn. To leave your current npm command untouched:

```sh
jup enable --exclude npm
```

## Easy to inspect

Run this whenever a command uses the wrong version or resolves from an unexpected location:

```sh
jup info
```

The report stays offline and shows:

- the project and pin jup found;
- the selected tool version;
- whether that version is cached; and
- which shims are active on `PATH`.

Use `jup info --json` in CI or support tooling.

## Corepack compatibility

jup keeps the parts projects already depend on:

- existing npm, pnpm, and Yarn `packageManager` pins;
- familiar package-manager commands through shims;
- `COREPACK_*` environment variables, alongside the preferred `JUP_*` names; and
- `.corepack.env` as a fallback when `.jup.env` is absent.

If both forms of an environment variable are set, `JUP_*` wins.

jup uses its own cache, so installing it does not modify or reuse Corepack's cached tools. Its default cache is `~/.cache/jup` on Linux and `%LOCALAPPDATA%\jup` on Windows.

## Switch from Corepack

jup is published to npm. Follow [Start](./start) for installation details.

To switch:

```sh
corepack disable
npm install -g jup
jup enable
jup info
```

The jup package also provides a compatibility `corepack` command. If installation reports that `corepack` already exists, first find out whether it is a standalone npm package or part of your Node.js installation. Do not use `--force` until you have checked the path being replaced. The [Start](./start) guide provides safe migration steps.

To roll back:

```sh
jup disable
npm uninstall -g jup
```

Then reinstall or repair Corepack using the method that originally supplied it, and run `corepack enable`.
