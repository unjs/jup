# Troubleshooting

Start with:

```sh
jup info
```

It stays offline, reports every invalid project setting instead of stopping at the first one, and never prints credential values. Use `jup info --json` for automation.

## The wrong command or version runs

Check **Project**, **Resolution**, and **Shims** in `jup info`. jup can only select a version through a jup shim or `jup <manager>`.

On POSIX, compare paths and clear the shell cache:

```sh
command -v pnpm
hash -r
```

In PowerShell, use `Get-Command pnpm` and open a new session after changing `PATH`. Move jup's printed shim directory earlier on `PATH` if another installation wins.

A strict pnpm project rejects Yarn — use the declared manager instead. A version-only override still has to keep its identity, such as `jup pnpm@11.22.0 --version`. To switch permanently, use `jup use yarn@<version>`. `JUP_ENABLE_STRICT=0` deliberately runs a different manager's default outside pinned projects — it doesn't run the project's own pin.

## jup found the wrong project

`jup info` shows the manifest or `JUP_SPEC_FILE` source. Remove accidental ancestor declarations, or target the current directory:

```sh
jup use --here pnpm@11
```

`--here` can create `package.json`. A malformed child manifest stops upward discovery. `JUP_SPEC_FILE` is resolved from the starting directory, must exist, overrides normal manifest discovery, and can't come from `.jup.env`.

## A shim conflicts or cannot be installed

A foreign regular command is normally warned about and skipped. Inspect its path before forcing a replacement:

```sh
command -v pnpm
jup enable --force
```

`jup disable` restores whatever jup recorded when displacing a command, and leaves unrelated changes alone. For a read-only directory, use a user-owned directory that's already on `PATH`:

```sh
jup enable --install-directory "$HOME/bin"
```

If `enable` succeeds but an old command still runs, fix `PATH`, restart the shell, clear its command cache, and check the **Shims** report again.

## A range works locally but fails in CI

Normal commands freeze `.jup.lock` when `CI` is set. Refresh and commit it:

```sh
jup up
git diff -- package.json .jup.lock
```

An explicit `jup up` is still allowed under CI's default freeze. Only an explicit `JUP_FROZEN_LOCKFILE=1` blocks it. Set `JUP_FROZEN_LOCKFILE=0` only for an intentional CI lock-update job.

## jup is offline or a version is missing

List the trusted local cache:

```sh
jup cache list
```

While connected, seed the project or an exact version:

```sh
jup install
jup install -g --cache-only pnpm@11.1.2
```

For an air-gapped host, create `jup pack` output on a trusted compatible machine and import it without changing the default outside pinned projects:

```sh
JUP_ENABLE_NETWORK=0 jup install -g --cache-only package-managers.tgz
```

Import doesn't authenticate or reverify the archive — use an authenticated trusted transfer, or independently verify a published checksum/signature first. `JUP_ENABLE_NETWORK=0` only controls jup and doesn't make the archive trustworthy. Use the executed package manager's own offline option and dependency cache separately.

## A registry request fails

Check the **Package managers** and **.npmrc** sections of `jup info`. Source precedence goes manager-specific `JUP_REGISTRY_<NAME>`, then `JUP_NPM_REGISTRY`, then applicable `.npmrc`, then the built-in source.

- Confirm a per-manager mirror preserves that source's expected paths.
- Put secrets in the process environment or user/global `.npmrc` — project auth/TLS entries are ignored.
- Configure `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY` and `NO_PROXY` when you need to.
- Increase `JUP_NETWORK_TIMEOUT` for a reachable but slow source.
- A true 404 for an exact version usually means it doesn't exist at the selected source, not a retryable outage.
- Check `JUP_MINIMUM_RELEASE_AGE` when no release seems old enough. It must be a non-negative number of hours, and sources with no usable date fail closed.

## TLS certificate verification fails

Use a complete company root bundle:

```sh
JUP_CAFILE=/path/to/all-required-roots.pem jup install
```

It replaces the platform trust store. Registry/proxy owners need to fix expiry or hostname mismatches on their end. `JUP_STRICT_SSL=0` is diagnostic only, and it warns whenever a request uses it — don't make it permanent.

## Download verification fails

Don't weaken verification until you've confirmed the manifest, lockfile, source, and publisher artifact.

### The digest does not match

The bytes differ from the project or lockfile pin. Check recent diffs and registry/mirror selection. Never paste an unexpected source's reported digest into the project.

### The signing key is unknown

Let jup refresh keys from npm's official endpoint, update jup, or check a fixed `JUP_INTEGRITY_KEYS` trust store.

### An expired-key signature does not verify

jup accepts a valid historical signature under the only matching expired key, with a prominent warning. This error means verification also failed. Check mirror integrity and provenance, and only pin a digest after independent verification.

### Registry metadata has no signature

By default, jup can fall back to the registry's digest with a warning. `JUP_REQUIRE_SIGNATURES=1` deliberately rejects that fallback — use signed metadata or a trusted project digest instead, if policy allows it.

### There is no signature or digest

After independently checking publisher provenance, scope the bootstrap to one command:

```sh
JUP_ALLOW_UNVERIFIED=1 jup use yarn@4
```

Review and commit the resulting digest, then confirm `jup install` works without the override. See [Download verification](./security).

## A repository setting is ignored

Credentials, CA/trust controls, unsafe URLs, unverified mode, `JUP_SPEC_FILE`, and `JUP_QUIET_ADVISORIES` can't come from `.jup.env`. Move them to user/CI process environment. Move project `.npmrc` credentials and TLS settings to user/global `.npmrc`. Security-sensitive entries produce a warning; `JUP_ENV_FILE` and the download-prompt setting can be silently ignored when placed inside the file.

`.jup.env` **can** choose `JUP_HOME`, which selects trusted executable cache state and shim restoration records. Override it in the process environment for untrusted repositories, and use the same trusted value for `jup enable` and `jup disable`.

## Node.js is too old or unavailable

The current JavaScript distribution of jup requires Node.js 22.18 or newer to start, before it can select any manager. Install or select a supported Node.js runtime in your shell, then rerun `jup --version`. `JUP_NODE_EXECPATH` is reserved for compatibility but isn't currently an effective remedy.

## `package.json` is invalid

Fix JSON syntax first. `"packageManager": null` and a bare `"packageManager": "pnpm"` are both invalid. A minimal exact declaration is:

```json
{ "packageManager": "pnpm@11.1.2" }
```

Prefer `jup use pnpm@11.1.2`, which adds a verified digest for you.

## Collect details for a bug report

```sh
jup info --json > jup-info.json
```

Review and redact **every file and log** before attaching it. Include the jup version, OS/architecture, exact command, and relevant stdout/stderr only after that review. `jup info` masks credential values, but package-manager stdout/stderr and other logs aren't guaranteed to be masked, and may contain tokens, URLs, paths, or project data.
