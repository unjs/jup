# Security

> Before jup adds a package manager to its cache, it requires at least one usable integrity check.

Protect `JUP_HOME`. It stores executable manager code, default-version records, and signing keys. For cached versions without a requested digest, jup trusts its completed installation record instead of checking the registry again.

::warning
`.jup.env` can choose `JUP_HOME`. A repository can therefore point jup to a different set of trusted executable files, even though it cannot directly disable verification. Use jup only in trusted repositories and paths. Review `.jup.env` changes. When working with untrusted code, set `JUP_HOME` in your process environment to override the repository value. Use the same trusted `JUP_HOME` for `jup enable` and `jup disable` because it also stores shim restoration records.
::

## Which check jup uses

jup tries these checks in order and uses the first one available:

1. **Project digest.** jup compares the download with a digest in the `packageManager` suffix, `devEngines.packageManager.integrity`, or `.jup.lock`. A project digest takes priority over the requirement for a registry signature, even with `JUP_REQUIRE_SIGNATURES=1`.
2. **Registry signature.** For npm packages, jup checks signed metadata with a trusted key.
3. **Registry digest.** If signed metadata is not available, jup can compare the download with a digest from the registry and print a warning. This detects damage during transfer, but it trusts the selected registry to provide the correct digest.

If no signature or digest is available, jup refuses the download. `JUP_REQUIRE_SIGNATURES=1` also rejects the registry-digest fallback unless the project has its own digest.

Portable exact pins give every host the same expected bytes. Native aube, Bun, Deno, nub, and Node downloads differ by host, so their exact manifest pin stays bare, and range lockfiles hold host-specific integrity instead.

## Bootstrap an otherwise unverified source

Use this exception only after checking the publisher's checksum or signature through a separate, trusted source:

```sh
JUP_ALLOW_UNVERIFIED=1 jup use yarn@4
git diff -- package.json .jup.lock
jup install
```

Set it for one command only. Check the digest that jup wrote, then confirm the normal command works without the override. Never set this option globally.

Direct Yarn Berry downloads from `repo.yarnpkg.com` often lack usable signature or digest metadata. Instead, you can configure an npm-compatible registry so jup obtains signed `@yarnpkg/cli-dist`, or use the careful one-command bootstrap above.

## Native managers and portable caches

For aube, Bun, Deno, nub, and Node, jup chooses and verifies the artifact for the current host. Range lockfiles record host-specific integrity. Only use caches and archives on a matching OS, architecture, and, on Linux, compatible C library. Unsupported hosts fail before any download starts.

## Signing keys and organisation policy

If jup finds an unknown npm key ID, it can refresh keys once from npm's official key endpoint. It caches the new keys under `JUP_HOME`, so they keep working offline and after cache cleanup. `JUP_INTEGRITY_KEYS=<json>` replaces the built-in keys and turns off automatic refresh. Set it in the user or CI environment, never in repository files.

A valid historical package signed by the only matching expired key is accepted with a prominent warning. If its signature doesn't verify, jup rejects it.

::warning
`JUP_INTEGRITY_KEYS=0` or an empty value disables registry verification and permits otherwise-unverified unpinned artifacts. A project-pinned digest is still checked regardless. Use this only as a deliberate, process-scoped policy exception.
::

## What repository configuration may change

Repository files have limited but real authority:

- `.jup.env` can choose `JUP_HOME`, along with certain allowed behavior and registry-routing settings. Because this selects executable cache state and shim restoration records, only trust a repository or path that deserves it, or override it in the process environment.
- `.jup.env` can't provide credentials, trust keys, CA files, disabled TLS, unsafe URLs, spec-file overrides, advisory muting, or unverified opt-outs.
- A project `.npmrc` can select a registry but can't provide credentials or TLS settings.
- A repository-selected registry still influences where metadata comes from. Verification stays active, but a registry-digest fallback still trusts that registry.
- User and CI credentials stay scoped to their configured origin or `.npmrc` host/path.

These limits reduce what a repository can change, but they do not make an untrusted checkout safe. Review changes to env files and registry routing. Use a trusted process-level `JUP_HOME` for untrusted work, and never restore it from an untrusted CI job.

Offline archives also require trust. Import does not authenticate them or verify their contents again. `JUP_ENABLE_NETWORK=0` does not make them safe. Accept archives only through an authenticated, trusted transfer or after separately checking a published checksum or signature.

## If verification fails

Do not copy the reported "got" digest into the project or disable checks until you have separately verified the manifest, `.jup.lock`, registry or mirror, and publisher file.

- **Digest mismatch:** investigate why the bytes or source changed.
- **Unknown key:** allow the official npm key refresh, update jup, or check your fixed trust store.
- **Expired-key verification failure:** the historical signature didn't verify. Check mirror integrity and provenance, then pin a trusted digest only once you've independently established it.
- **Unsigned metadata:** use a signed source, accept the warned registry digest under policy, or pin a trusted project digest.

See [Troubleshooting](./troubleshooting#download-verification-fails) for command-by-command remedies.
