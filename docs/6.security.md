# Download verification

Before jup adds a package manager to its cache, it requires one usable integrity check. Protect `JUP_HOME`: it contains executable manager code, default-version records, and signing keys, and warm unpinned entries are trusted from jup's completed installation record rather than reverified with the registry.

::warning
`.jup.env` is allowed to choose `JUP_HOME`. A repository can therefore point jup at different trusted executable state even though it cannot directly disable verification. Use jup only in trusted repositories and paths, review `.jup.env` changes, and override `JUP_HOME` from your process environment when working with untrusted code. Run `jup enable` and `jup disable` with the same trusted `JUP_HOME`, because shim restoration records are stored there.
::

## Which check jup uses

The checks are alternatives, in this order:

1. **Project digest.** A suffix in `packageManager`, `devEngines.packageManager.integrity`, or `.jup.lock` is compared with the download. An explicit project digest takes precedence instead of also requiring a registry signature, even under `JUP_REQUIRE_SIGNATURES=1`.
2. **Registry signature.** For npm packages, jup verifies signed metadata with a trusted key.
3. **Registry digest.** If signed metadata is unavailable, jup may compare the download with the registry-supplied digest and warn. This protects against transfer corruption but trusts the selected registry to provide the expected value.

If neither signature nor digest is available, jup refuses the download. `JUP_REQUIRE_SIGNATURES=1` also refuses the registry-digest fallback, unless the project already pins its own digest.

Portable exact pins give all hosts the same expected bytes. Native aube, Bun, Deno, nub, and Node downloads differ by host, so their exact manifest pin is bare and range lockfiles hold host-specific integrity.

## Bootstrap an otherwise unverified source

Use an opt-out only after checking the publisher's checksum or signature through an independent trusted channel:

```sh
JUP_ALLOW_UNVERIFIED=1 jup use yarn@4
git diff -- package.json .jup.lock
jup install
```

Scope it to one command, inspect the written digest, and confirm the normal command succeeds without the override. Never export this setting globally.

Direct Yarn Berry downloads from `repo.yarnpkg.com` often lack usable signature/digest metadata. You can instead configure an npm-compatible registry so jup obtains signed `@yarnpkg/cli-dist`, or use the careful one-command bootstrap above.

## Native managers and portable caches

For aube, Bun, Deno, nub, and Node, jup chooses and verifies the artifact for the current host. Range lockfiles record host-specific integrity. Use caches and archives only on a matching OS, architecture, and—on Linux—compatible C library. Unsupported hosts fail before download.

## Signing keys and organisation policy

Unknown npm key IDs can trigger a one-time refresh from npm's official key endpoint. Refreshed keys are cached under `JUP_HOME` and remain usable offline and after cache cleanup. A fixed `JUP_INTEGRITY_KEYS=<json>` trust store replaces built-in keys and disables automatic refresh; supply it through user/CI environment, never repository files.

A valid historical package signed by the only matching expired key is accepted with a prominent warning. If its signature does not verify, jup rejects it.

::warning
`JUP_INTEGRITY_KEYS=0` or an empty value disables registry verification and permits otherwise-unverified unpinned artifacts. A project-pinned digest is still checked. Use this only as an intentional, process-scoped policy exception.
::

## What repository configuration may change

Repository files have limited—but important—authority:

- `.jup.env` may choose `JUP_HOME` as well as allowed behavior and registry-routing settings. Because this selects executable cache state and shim restoration records, trust the repository/path or override it in the process environment.
- `.jup.env` may not provide credentials, trust keys, CA files, disabled TLS, unsafe URLs, spec-file overrides, advisory muting, or unverified opt-outs.
- A project `.npmrc` may select a registry but cannot provide credentials or TLS settings.
- A repository-selected registry still influences the source of metadata. Verification remains active, but a registry-digest fallback trusts that registry.
- User and CI credentials remain scoped to their configured origin or `.npmrc` host/path.

These restrictions reduce repository authority; they do not make an untrusted checkout safe. Review env-file and routing changes, keep a trusted process-level `JUP_HOME` for untrusted work, and never restore it from an untrusted CI job.

Offline archives are another trust boundary. Import does not authenticate or reverify their contents, and `JUP_ENABLE_NETWORK=0` does not make them safe. Accept archives only through authenticated trusted transfer or after independently checking a published checksum or signature.

## If verification fails

Do not copy the reported “got” digest into the project or disable checks until you have confirmed the manifest, `.jup.lock`, registry/mirror, and publisher artifact independently.

- **Digest mismatch:** investigate why the bytes or source changed.
- **Unknown key:** allow the official npm key refresh, update jup, or check your fixed trust store.
- **Expired-key verification failure:** the historical signature did not verify; check mirror integrity and provenance, then pin a trusted digest only if independently established.
- **Unsigned metadata:** use a signed source, accept the warned registry digest under policy, or pin a trusted project digest.

See [Troubleshooting](./troubleshooting#download-verification-fails) for command-by-command remedies.
