# CI and offline

> jup's cache and your package manager's dependency cache are separate.

`JUP_ENABLE_NETWORK=0` stops **jup** from resolving or downloading a package manager, but it doesn't stop npm, pnpm, Yarn, or another manager from talking to its own dependency registry.

## Warm the package manager cache

While connected, run:

```sh
jup install
jup cache list --json
```

`jup install` caches the manager selected by the current project. It does not change project pins, write `.jup.lock`, or change the default used outside pinned projects. For a range or tag, first create and commit the resolution using one of the workflows below. `jup install` then caches that recorded version.

For pnpm, cache the project dependencies while you are online. Use a committed `pnpm-lock.yaml`:

```sh
jup install
pnpm fetch --frozen-lockfile
```

Then test offline using both controls:

```sh
# JUP_ENABLE_NETWORK controls jup; --offline controls pnpm.
JUP_ENABLE_NETWORK=0 pnpm install --offline --frozen-lockfile
```

`jup install` only prepares the package-manager executable — it doesn't fetch project dependencies. npm, Yarn, and other managers have their own cache-preparation and offline commands, so follow that manager's documentation for those.

## Use jup in CI

For an exact pin, a typical pnpm job restores two trusted caches: the jup cache and a dependency store created with `pnpm fetch`. It then runs:

```sh
jup install
JUP_ENABLE_NETWORK=0 pnpm install --offline --frozen-lockfile
```

If `packageManager` contains a semantic version (semver) range, create or refresh `.jup.lock` locally with `jup up`. Review and commit the manifest, lockfile, and dependency changes. When `CI` is set, normal commands refuse to create or refresh a missing or stale range resolution. You can still run `jup up` explicitly under CI's default. Only `JUP_FROZEN_LOCKFILE=1` blocks it. Set `JUP_FROZEN_LOCKFILE=0` only in a job meant to update the lockfile.

A retained registry tag also needs a committed `.jup.lock`, but `jup up` rejects tags. Create its first resolution outside frozen mode with a normal manager command, such as `jup pnpm --version`. To deliberately follow the tag again, remove that tag's entry from `.jup.lock`, rerun the command while connected, and review the new resolution before committing it. Or run `jup use pnpm@latest`, which resolves the tag now and replaces it with an exact pin. See [Projects and workspaces](./projects-and-workspaces#keep-a-registry-tag-in-packagemanager) for the full workflow.

You can save `JUP_HOME` between jobs. Include the operating system and architecture in the cache key. Where needed, include the Linux C library too. Native aube, Bun, Deno, nub, and Node entries depend on the host system. `JUP_HOME` contains executable code that jup trusts on a cache hit. Restore it only from trusted jobs, never from untrusted forks or uploads. Run `jup info` to see the path in use.

## Build a container image

The image needs Node.js 22.18 or newer, jup installed, and its pnpm shim enabled before these steps (or replace each `pnpm` command with `jup pnpm`). For the common exact-pin case, don't copy a `.jup.lock` file that may not exist:

```dockerfile
COPY package.json pnpm-lock.yaml ./
RUN jup install && pnpm fetch --frozen-lockfile
ENV JUP_ENABLE_NETWORK=0
COPY . .
RUN pnpm install --offline --frozen-lockfile
```

For a range or tag pin, commit `.jup.lock` and add it to the first `COPY`:

```dockerfile
COPY package.json .jup.lock pnpm-lock.yaml ./
RUN jup install && pnpm fetch --frozen-lockfile
```

This puts the manager and dependency caches in reusable image layers. For other managers, use their equivalent dependency-cache commands.

## Cache a specific release

Seed one release without touching a project or the default used outside pinned projects:

```sh
jup install -g --cache-only pnpm@12.1.2
jup cache list
```

If an offline command reports a missing version, run this on a connected trusted machine, or import an archive as described below.

## Transfer an offline archive

On a connected machine:

```sh
jup pack -o package-managers.tgz pnpm@12.1.2
```

On the source machine, `pack` also makes each packed version the default outside pinned projects. On the target machine, import the cache without changing its defaults:

```sh
JUP_ENABLE_NETWORK=0 jup install -g --cache-only package-managers.tgz
jup cache list --json
```

Without `--cache-only`, each imported version becomes the default outside pinned projects. Import does **not** authenticate the archive or verify its contents again. Transfer it through an authenticated, trusted channel. Or verify a published checksum or signature before importing it. `JUP_ENABLE_NETWORK=0` blocks network access, but does not make an archive safe. Archives with aube, Bun, Deno, nub, or Node must match the target operating system and architecture. On Linux, they must also use a compatible C library.

## Clear cached package managers

```sh
jup cache clean       # keep default-version records
jup cache clear       # exact alias
jup cache clean --all # also remove default-version records
```

Both cleanup modes keep the downloaded signing-key cache. Removed manager versions need to be downloaded or imported again. See [Security](./security) for cache trust and verification guidance.
