# CI and offline use

jup's cache and your package manager's dependency cache are separate. `JUP_ENABLE_NETWORK=0` prevents **jup** from resolving or downloading a package manager. It does not stop npm, pnpm, Yarn, or another manager from contacting its dependency registry.

## Warm the package manager cache

While connected, run:

```sh
jup install
jup cache list --json
```

`jup install` caches the manager selected by the current project and does not change the default used outside pinned projects. It does not change project pins or write `.jup.lock`. For a range or tag, create and commit the resolution first using the workflows below; `jup install` then warms the cache with that recorded version.

For pnpm, seed dependency data while still connected and with a committed `pnpm-lock.yaml`:

```sh
jup install
pnpm fetch --frozen-lockfile
```

Then test offline using both controls:

```sh
# JUP_ENABLE_NETWORK controls jup; --offline controls pnpm.
JUP_ENABLE_NETWORK=0 pnpm install --offline --frozen-lockfile
```

`jup install` prepares only the package-manager executable; it does not fetch project dependencies. npm, Yarn, and other managers use different cache-preparation and offline commands, so follow that manager's documentation.

## Use jup in CI

For an exact pin, a typical pnpm job restores a trusted jup cache and a dependency store previously populated with `pnpm fetch`, then runs:

```sh
jup install
JUP_ENABLE_NETWORK=0 pnpm install --offline --frozen-lockfile
```

If `packageManager` contains a semver range, create or refresh `.jup.lock` locally with `jup up`, review the manifest, lockfile, and dependency changes, then commit them. With `CI` set, normal commands refuse to create or refresh a missing or stale range resolution. An explicit `jup up` is allowed under CI's default freeze, but `JUP_FROZEN_LOCKFILE=1` blocks it. Set `JUP_FROZEN_LOCKFILE=0` only in an intentional lock-update job.

A retained registry tag also needs a committed `.jup.lock`, but `jup up` rejects tags. Create its first resolution outside frozen mode with a normal manager command, for example `jup pnpm --version`. To deliberately follow the tag again, remove that tag's entry from `.jup.lock`, rerun the command while connected, and review the new resolution before committing it. Alternatively, `jup use pnpm@latest` resolves the tag now and replaces it with an exact pin. See [Projects and workspaces](./projects-and-workspaces#keep-a-registry-tag-in-packagemanager) for the full workflow.

You can persist `JUP_HOME` between jobs. Include the operating system and architecture in the cache key, and include the Linux C library when relevant. Native aube, Bun, Deno, and nub entries are host-specific. The directory contains executable code that jup trusts on a cache hit, so restore it only from trusted jobs—not untrusted forks or uploads. Run `jup info` to see the effective path.

## Build a container image

The image must provide Node.js 22.18 or newer, install jup, and enable its pnpm shim before these steps (or replace each `pnpm` command with `jup pnpm`). For the common exact-pin case, do not copy a `.jup.lock` file that may not exist:

```dockerfile
COPY package.json pnpm-lock.yaml ./
RUN jup install && pnpm fetch --frozen-lockfile
ENV JUP_ENABLE_NETWORK=0
COPY . .
RUN pnpm install --offline --frozen-lockfile
```

For a range or tag pin, commit `.jup.lock` and add it to the first `COPY`:

```dockerfile
COPY package.json .jup.lock pnpm-lock.yaml ./
RUN jup install && pnpm fetch --frozen-lockfile
```

This keeps manager and dependency preparation in reusable layers. Use the equivalent dependency-cache commands for managers other than pnpm.

## Cache a specific release

Seed one release without changing a project or the default used outside pinned projects:

```sh
jup install -g --cache-only pnpm@11.1.2
jup cache list
```

If an offline command says a version is missing, run this on a connected trusted machine or import an archive as described below.

## Transfer an offline archive

On a connected machine:

```sh
jup pack -o package-managers.tgz pnpm@11.1.2
```

`pack` also makes every packed version the default outside pinned projects on the source machine. On the target, seed the cache without changing those defaults:

```sh
JUP_ENABLE_NETWORK=0 jup install -g --cache-only package-managers.tgz
jup cache list --json
```

Without `--cache-only`, archive import makes each imported version the default outside pinned projects. Import does **not** authenticate the archive or reverify its contents. Transfer it through an authenticated trusted channel, or independently verify a published checksum or signature before import. `JUP_ENABLE_NETWORK=0` prevents network access; it does not make an archive trustworthy. Archives containing aube, Bun, Deno, or nub must be built for the target's OS, architecture, and—on Linux—compatible C library.

## Clear cached package managers

```sh
jup cache clean       # keep default-version records
jup cache clear       # exact alias
jup cache clean --all # also remove default-version records
```

Both cleanup modes keep the downloaded signing-key cache. Removed manager versions must be downloaded or imported again. See [Download verification](./security) for cache trust and verification guidance.
