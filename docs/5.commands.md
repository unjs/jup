# Commands

## Run a package manager

After `jup enable`, use the commands you already know:

```sh
pnpm install
jup pnpm install       # same route without a shim
jup pnpm@12.22.0 --version
```

In a strict project, a one-command version override must still use the required manager. `jup --version` prints the jup version. `jup pnpm --version` prints the pnpm version.

## Choose a project version

```sh
jup use pnpm@12
```

The selector can be a bare name (the latest stable version), an exact version, a range, or a tag. `use` resolves it, verifies and caches the release, writes the pin, and prints each changed path. It then runs the manager's install command. Review changes to dependencies, lockfiles, and `package.json`.

A **range** is kept as written: `jup use pnpm@^12.0.0` leaves `^12.0.0` in `packageManager` and records the release it selected in `jup.lock`. Every other selector writes an exact pin and no lockfile.

```sh
jup up
```

For an exact pin, `up` stays within the current major version unless `devEngines.packageManager.version` allows a different range. For a semver range — in `packageManager`, or in `devEngines.packageManager.version` when the manifest has no top-level pin — it keeps the range and updates only `jup.lock`. It rejects registry tags, which are never recorded. See [Projects](./projects#keep-a-registry-tag-in-packagemanager).

`use` and `up` are the only commands that write `jup.lock`. Running a package manager never does; it caches its answer in `node_modules/.jup/jup.lock` instead. `JUP_FROZEN_LOCKFILE=1` makes both commands fail rather than change `jup.lock` — including an exact `jup use` that would retire the recorded resolution of the range it replaces.

Both commands accept:

- `--here`, which targets the current directory's `package.json`. `use --here` can create it; `up --here` requires an existing usable pin;
- `--pin-style=suffix` (default), which appends the digest to `packageManager`;
- `--pin-style=sidecar`, which writes the digest to `devEngines.packageManager.integrity`.

Native aube, Bun, Deno, nub, and Node pins stay digest-free, since their artifacts differ by host. Node is pinned in `devEngines.runtime` rather than `packageManager`, and `jup use node@…` writes the pin without running an install command. See [Projects](./projects).

## Prepare for CI or offline use

```sh
jup install
```

This caches the version selected by the current project. It does not change the project pin, `jup.lock`, or the default used outside pinned projects. For a range, commit `jup.lock` first, so the layer caches the release the build will actually run. With nothing committed, `install` uses an unexpired entry from `node_modules/.jup/jup.lock`, so a warmed layer and the run it warms never disagree.

```sh
jup install -g --cache-only pnpm@12.1.2
```

Caches named versions without changing the default used outside pinned projects. This form can also import an archive without activating its contents:

```sh
jup install -g --cache-only tools.tgz
```

Create an archive with:

```sh
jup pack -o tools.tgz pnpm@12.1.2
jup pack --json -o tools.tgz pnpm@12.1.2
```

The default output is `jup.tgz`. On the source machine, `pack` also makes the packed versions the defaults outside pinned projects. On the target machine, `jup install -g tools.tgz` imports and activates those versions. Import does not authenticate the archive or verify its contents again. First use a trusted transfer, checksum, or signature to verify it. See [CI](./ci).

## Manage defaults and cache

```sh
jup install -g pnpm@12.1.2
```

A **global fallback** is the default version jup uses outside a pinned project. This command downloads a release and makes it the default. It can replace a newer default. Add `--cache-only` if you only want to cache the release.

```sh
jup cache list
jup cache list --json
jup cache clean
jup cache clear       # alias
jup cache clean --all
```

`clean` removes downloaded versions but keeps default-version records. `--all` removes both. The signing-key cache always stays.

## Diagnose the current setup

```sh
jup info
jup info --json
```

`info` stays offline and reports all invalid settings instead of stopping at the first one. Programs that read its JSON output should ignore fields they do not recognize.

## Install or remove shims

```sh
jup enable
jup disable
```

Bare `enable` creates npm/npx, pnpm/pnpx, Yarn/yarnpkg, and aube/aubr/aubx shims. Bun/bunx, Deno, nub/nubx, and Node are opt-in:

```sh
jup enable bun deno nub node
```

`disable` with no arguments removes every jup-managed shim, including optional ones. Both commands accept `--install-directory`, manager names, and `--exclude` as a repeated or comma-separated option. `enable --force` replaces conflicting files. jup records what it replaced so `disable` can restore it. Read conflict and `PATH` warnings before using `--force`.

Defaults are user-owned: `$XDG_BIN_HOME` when set on non-macOS POSIX, otherwise `~/.local/bin` (including macOS), and `%LOCALAPPDATA%\jup\bin` on Windows.

`--system` installs machine-wide instead — `/usr/local/bin`, or `%ProgramData%\jup\bin` on Windows — which is what a container image or a shared machine usually wants. It needs write access to that directory, and unlike every other target it never quietly falls back to a user-owned one: if it can't write there, the command fails. Pass it to `disable` as well when a non-root user installed that way. Running as root, a bare `enable` already reaches `/usr/local/bin` when no user-owned directory is on `PATH`, and says so.

## Install jup itself

```sh
jup self-install
```

`self-install` copies the jup that is running into `<cache>/self/<version>` and links `jup` and `corepack` from the same directory `enable` uses.

Nothing is resolved and nothing is downloaded — the bytes it installs are the ones already executing — so the usual route is one throwaway run of jup making itself permanent:

```sh
npx jup self-install   # from npm, without a global install
```

The copy lives beside the cache rather than inside it, so `jup cache clean` never touches it. Re-running is free when nothing changed, and installs the new bytes when something did. It accepts `--install-directory`, `--system`, and `--force`; `--force` is what takes over a `corepack` that Node shipped.

Removing a self-install is a deliberate act: delete `<cache>/self` and the `jup` and `corepack` entries in your shim directory.

## Upgrade jup itself

```sh
jup self-upgrade      # or: jup upgrade
```

`self-upgrade` fetches the latest published jup, verifies it exactly as it verifies a package manager download — the registry's signature over the version, then the digest of the bytes as they arrive — and points the same two names at the new copy. The previous copy under `<cache>/self` is removed once the new one is on `PATH`, so the directory holds one jup rather than one per release.

It takes the same `--install-directory`, `--system` and `--force` as `self-install`, honours `COREPACK_NPM_REGISTRY` and your `.npmrc` registry, and does nothing beyond one metadata request when the newest version is the one already installed. It installs whatever the registry's `latest` tag names — so if you are running a prerelease that is ahead of it, this moves you back to the released version. Note that `upgrade` is not `up`: `up` updates this project's `packageManager` field, `self-upgrade` updates jup.

## Deprecated Corepack commands

`prepare` and `hydrate` still run, but each one prints a migration warning. Use `pack` instead of `prepare`, and `install -g <archive>` instead of `hydrate` in new automation. All help and usage examples use the name `jup`.
