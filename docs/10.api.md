# Programmatic API

> jup provides a small ESM API. Import it from the package root.

## Run the CLI

`runMain(argv)` runs the same management or proxy code as the `jup` command. It
returns a number for the exit code. It never calls `process.exit()`.

The array holds everything that comes after `jup` on the command line. This
example runs the pnpm version selected by the project:

```js
import { runMain } from "jup";

process.exitCode = await runMain(["pnpm", "install"]);
// Like: jup pnpm install
```

You can add a version to the binary name. This example runs Node.js 22 without a
shim:

```js
import { runMain } from "jup";

process.exitCode = await runMain(["node@^22", "script.js", "--verbose"]);
// Like: jup node@^22 script.js --verbose
```

Use the same function for management commands:

```js
process.exitCode = await runMain(["info", "--json"]);
// Like: jup info --json
```

Arguments, stdin, stdout, stderr, exit codes, and signals work in the same way as
they do in the CLI. See the [command reference](./commands). Two rules affect
where you can call `runMain()` in a script. A proxied JavaScript tool may take
over the current process. If a signal kills a proxied tool, the same signal also
kills the calling process. In that case, `runMain()` does not return an exit
code. Call `runMain()` only as the last operation in your script.

## Parse the arguments

`parseArgs(argv)` only checks how jup should route the arguments. It does not run
anything. It returns either a `proxy` invocation or a `management` invocation:

```js
import { parseArgs } from "jup";

parseArgs(["pnpm", "install"]);
// { mode: "proxy", binaryName: "pnpm", args: ["install"] }

parseArgs(["node@^22", "script.js"]);
// { mode: "proxy", binaryName: "node", args: ["script.js"], binaryVersion: "^22" }

parseArgs(["info", "--json"]);
// { mode: "management", args: ["info", "--json"] }
```

The result has `binaryVersion` only when the first argument includes
`@<version>`.

## Parse a specification

`parseSpec(raw, options)` changes user input into a `Spec`. Every option has a
default, so the second argument is optional:

```js
import { parseSpec } from "jup";

parseSpec("pnpm@^12");
// { name: "pnpm", range: "^12" }

parseSpec("pnpm");
// { name: "pnpm", range: "*" }
```

Set `requireVersion: true` to reject input that names no version. Set `source` to
name the input in the error message. It defaults to `CLI arguments`:

```js
parseSpec("pnpm", { requireVersion: true, source: "my script" });
// UsageError: No version specified for pnpm in "packageManager" of my script
```

Set `packageManagerField: true` when the string comes from a manifest's
`packageManager` field. jup will then reject a runtime name in the same way as
the CLI.

## Read a project pin

`findProjectSpec(cwd, options)` searches parent directories in the same way as
the CLI. It also follows the CLI rules for environment files. The result's `type`
is `Found`, `NoSpec`, or `NoProject`. Every result has a `target`. This is the
path of the manifest where the search stopped.

```js
import { findProjectSpec } from "jup";

const project = findProjectSpec(process.cwd(), { tool: "pnpm" });
project.type;   // "Found" | "NoSpec" | "NoProject"
project.target; // "/path/to/package.json"

if (project.type === "Found") {
  project.getSpec({ requireVersion: true });
  // { name: "pnpm", range: "^12" }
}
```

Use `tool: "node"` or another runtime name to read `devEngines.runtime` instead
of the package manager fields.

`getSpec()` parses the specification later. It takes the same options as
`parseSpec()`, except `source`, which the manifest supplies. Discovery can still
fail first. If a manifest contains invalid JSON, `findProjectSpec()` throws a
`UsageError`. The error does not come from `getSpec()`.

Discovery also loads the closest project environment file. It uses `.jup.env`,
or `.corepack.env` if `.jup.env` is not present. It copies allowed entries into
`process.env`. Existing environment variables take priority over entries in the
file. jup only copies entries allowed by
[Settings](./settings#project-env-files). In a long-running process, variables
from the first project file remain set when you search other projects.

## Resolve a version

`resolveSpec(spec, options)` returns a `ResolvedSpec`. It returns `null` if no
release matches:

```js
import { resolveSpec } from "jup";

await resolveSpec({ name: "pnpm", range: "^12" });
// { name: "pnpm", reference: "12.1.0" }

await resolveSpec({ name: "pnpm", range: "^99" });
// null
```

The field is `reference`, not `version`, because it also holds a URL, or an
exact version that carries a digest, such as `12.1.0+sha512.0123abcd…`.

If a matching version is already installed, jup resolves a range from the store.
Otherwise, it uses the configured registry. Pass `{ allowTags: true }` to allow
tags such as `latest`. Pass `{ useCache: false }` to make jup check the registry
when it resolves a range.

jup returns an exact version without checking whether it exists. This means a
version with a typo can resolve successfully. It will fail later when jup tries
to download it.

## Install a resolved version

`ensureInstalled(resolved, options)` takes a `ResolvedSpec` and returns an
`Installation`. If the store does not have the artifact, jup downloads and
verifies it:

```js
import { ensureInstalled } from "jup";

await ensureInstalled({ name: "pnpm", reference: "12.0.0" }, { cacheOnly: true });
// {
//   location: "/home/me/.cache/node/corepack/v1/pnpm/12.0.0",
//   bin: { pnpm: "./pnpm", pnpx: "./pnpm" },
//   hash: "sha512.0123abcd...",
// }
```

Set `cacheOnly` to warm the cache without updating the last-known-good fallback
information.

`bin` maps binary names to paths relative to `location`. The paths already match
the current platform. For example, the same entry uses `./pnpm.exe` on Windows.
`bin` is missing when the store marker has no paths. In that case, jup gets the
paths from its built-in entry for the tool.

If verification fails, jup throws an error and does not cache anything. Running
the call again will fail in the same way.

## Errors and types

jup uses `UsageError` for invalid user input. Examples include an invalid
specification, an unsupported name, or a version that the project does not
allow. Any other error means that an operation failed or jup has a bug. Do not
tell the user that these other errors are their fault:

```js
import { parseSpec, UsageError } from "jup";

try {
  parseSpec(process.argv[2], { requireVersion: true });
} catch (error) {
  if (!(error instanceof UsageError)) throw error;
  console.error(error.message);
  // No version specified for pnpm in "packageManager" of CLI arguments
  process.exitCode = 1;
}
```

The package also exports TypeScript types. The four that carry the pipeline are
`Spec`, `ResolvedSpec`, `Installation`, and `ProjectSpec`. `Invocation` and
`ParseSpecOptions` cover the two functions that take arguments of their own.
