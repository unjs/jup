# Projects and workspaces

A project pin tells jup which package manager to run. jup reads the pin from `package.json` and supports both the `packageManager` field and Node's `devEngines.packageManager` object.

## Pin an exact version

The usual form is:

```json
{
  "packageManager": "pnpm@11.1.2+sha512.abc123..."
}
```

The suffix contains a digest of the downloaded package manager. jup verifies a new download before putting it in the cache. On later runs it checks that jup's completed cache record matches the requested pin; it does not rehash every cached file on every command. Treat the cache as trusted executable state.

You do not need to calculate or enter the digest yourself. Run:

```sh
jup use pnpm@11
```

Although `pnpm@11` is a range, `jup use` resolves it immediately and writes an exact version and digest.

Other accepted selectors include:

```sh
jup use pnpm@11.1.2   # exact version
jup use pnpm@^11.0.0  # semantic version range
jup use pnpm@latest   # registry tag
jup use pnpm          # current stable release
```

These are command-line selectors. A project declaration must include a selector, such as `"packageManager": "pnpm@11"`; a bare `"pnpm"` value in `package.json` is invalid.

Automatic selection excludes prereleases such as `12.0.0-beta.1`. To use one, request it explicitly, provide a range that includes prereleases, or set `JUP_ENABLE_PRERELEASES=1`.

## Use `devEngines.packageManager`

Node also supports a structured declaration:

```json
{
  "devEngines": {
    "packageManager": {
      "name": "pnpm",
      "version": "11.x",
      "onFail": "error"
    }
  }
}
```

`version` may be exact or a semver range. `onFail` defaults to `error`: `error` stops on a mismatch, `warn` prints a warning and continues, and `ignore` continues silently. Severely malformed declarations may still warn because jup cannot reliably apply their policy.

If this is the project's only declaration, `jup use` updates it in place to an exact version plus `integrity`; it does not add `packageManager`. When both forms exist, an exact `devEngines` version is updated too, while a range remains an additional constraint.

When both forms are present, `packageManager` supplies the active pin and `devEngines.packageManager` supplies an additional constraint. jup checks that they agree.

For example, this manifest pins one release while allowing any pnpm 11 release:

```json
{
  "packageManager": "pnpm@11.1.2+sha512.abc123...",
  "devEngines": {
    "packageManager": {
      "name": "pnpm",
      "version": "11.x",
      "onFail": "error"
    }
  }
}
```

When `jup up` updates the exact pin, it preserves the `11.x` constraint rather than replacing it with an exact version.

## Keep a range in `packageManager`

A manifest may contain a range directly:

```json
{
  "packageManager": "pnpm@^11.0.0"
}
```

A range can resolve differently as releases appear. To make the result repeatable, jup records the selected release and digest in `.jup.lock`:

```json
{
  "version": 1,
  "resolutions": {
    "pnpm@^11.0.0": {
      "resolved": "11.1.2",
      "integrity": "sha512-..."
    }
  }
}
```

After writing the range, create or refresh its resolution locally with:

```sh
jup up
```

`jup up` preserves the range in `packageManager`, updates only its `.jup.lock` resolution, and runs the selected manager's install command. Review and commit both the dependency changes and `.jup.lock`. Future runs use the recorded release without asking the registry which version matches.

This differs from passing a range to `jup use`: `jup use pnpm@^11` resolves immediately and writes an exact pin. A range remains only when it is already in `packageManager`, for example because it was written manually or by another tool.

When `CI` is set, normal commands freeze range resolutions by default. A missing or stale entry then fails instead of changing during the build. An explicit `jup up` remains an intentional refresh under CI's default, but `JUP_FROZEN_LOCKFILE=1` blocks it. Set `JUP_FROZEN_LOCKFILE=0` only in a deliberate CI update job.

## Keep a registry tag in `packageManager`

A retained tag also uses `.jup.lock`:

```json
{
  "packageManager": "pnpm@latest"
}
```

`jup up` does **not** accept tags. To create the first resolution, run a normal manager command while connected and outside frozen mode:

```sh
jup pnpm --version
```

That resolves `latest`, caches and verifies the selected release, and records it under `pnpm@latest` in `.jup.lock`. Commit the file; later commands keep using that recorded release even if the registry moves the tag.

To deliberately follow the same tag again while retaining `pnpm@latest`, remove its `pnpm@latest` entry from `.jup.lock` (or remove the file if it contains no other resolutions), then run the normal command again and review the new lockfile. To follow a different channel, change the manifest to that tag, such as `pnpm@next`, and run the command to create its new entry.

If you no longer need the tag retained, this simpler command asks the registry what it means now and writes the result as an exact pin:

```sh
jup use pnpm@latest
```

`jup use` also runs the selected manager's install command. Review its manifest, dependency, and lockfile changes. Exact `packageManager` pins do not need `.jup.lock`.

## Pin aube, Bun, Deno, or nub

aube, Bun, Deno, and nub are pinned like any other package manager:

```json
{
  "packageManager": "bun@1.4.0"
}
```

```sh
jup use aube@2.2.0
jup use bun@1.4.0
jup use deno@2.9.5
jup use nub@0.7.5
```

One difference is visible in the file: there is **no digest suffix**. These managers publish different downloads for each supported host, so one digest in `packageManager` would not be portable. jup still verifies the artifact selected for the current host before caching it. See [Download verification](./security).

With a range, `.jup.lock` records one digest per host:

```json
{
  "version": 1,
  "resolutions": {
    "bun@^1.4.0": {
      "resolved": "1.4.0",
      "integrity": {
        "linux-x64": "sha512-...",
        "darwin-arm64": "sha512-..."
      }
    }
  }
}
```

The version is shared, while each host needs its own digest entry. Under frozen mode, a new CI host cannot add a missing entry. Run the range once on every target OS/architecture (and each Linux C-library variant) before freezing and commit the combined `.jup.lock`, or deliberately refresh it in a trusted unfrozen job. If a release has no build for the current host, jup reports that before downloading.

See [Getting started](./getting-started) to choose which optional shims to enable.

## Pin Node.js

Node is a runtime, not a package manager, so it is pinned in `devEngines.runtime`:

```sh
jup use node@22
```

```json
{
  "packageManager": "pnpm@11.1.2+sha512...",
  "devEngines": {
    "runtime": {
      "name": "node",
      "version": "22.23.2"
    }
  }
}
```

Three things follow from Node being a runtime, and they are the whole difference:

- **`packageManager` may not name it.** jup refuses a manifest that says `"packageManager": "node@22"` and points you at `devEngines.runtime`. That field is what jup enforces when you run the *wrong package manager* in a project, and a runtime is not one.
- **The two fields do not constrain each other.** A project can pin pnpm and Node in the same manifest; each speaks for its own tool. Running `node` in a pnpm project is never a mismatch error, and running `pnpm` there is unaffected by the Node declaration.
- **`jup use node@…` writes the pin and stops.** There is no install command to run afterwards, unlike `jup use pnpm@…`.

Like the native package managers above, the pin carries no digest suffix—Node publishes a different download per host—and a range records one digest per host in `.jup.lock`.

Node's `node` shim is opt-in for the same reason Bun's and Deno's are, and more so: `node` almost certainly already names something on your machine. `jup enable node` claims it deliberately.

::note
Node publishes no musl build, so on Alpine and other musl Linux hosts jup reports that before downloading rather than caching a binary that cannot start. `linux-armv7l` is likewise outside the set jup can name.
::

## Choose which manifest to edit

By default, commands that write a pin walk up from the current directory and stop at a manifest with `workspaces` or a directory containing `pnpm-workspace.yaml`. Commands that only read a pin may continue upward, so nested packages can inherit the workspace pin. jup prints the exact path it changed.

Use `--here` to target `package.json` in the current directory:

```sh
jup use --here pnpm@11.1.2
jup up --here
```

If there is no manifest, `jup use --here` may create one. `jup up --here` cannot create a manifest: it requires an existing usable project pin in that directory.

Manifest lookup is broader when jup only needs to read a pin. A package without its own declaration may inherit one from a parent, which lets a single workspace pin apply to all packages.

## Choose where to store the digest

By default, jup appends the digest to `packageManager`. This **suffix** style works with Corepack:

```json
{
  "packageManager": "yarn@4.14.1+sha512.abc123..."
}
```

Some tools accept only a plain version in `packageManager`. For those projects, use the **sidecar** style:

```sh
jup use --pin-style=sidecar yarn@4.14.1
```

It writes the digest separately:

```json
{
  "packageManager": "yarn@4.14.1",
  "devEngines": {
    "packageManager": {
      "name": "yarn",
      "version": "4.14.1",
      "integrity": "sha512-..."
    }
  }
}
```

jup verifies both styles. Use the default suffix for Corepack interoperability unless another tool specifically requires plain version text. The sidecar is jup-specific; tools that ignore it see only the exact version.

Run `jup info` from any package when you need to see which manifest and declaration jup selected.
