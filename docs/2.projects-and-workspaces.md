# Projects and workspaces

A project pin tells jup which package manager to run. jup reads the pin from `package.json`, in either the `packageManager` field or Node's `devEngines.packageManager` object.

## Pin an exact version

The usual form is:

```json
{
  "packageManager": "pnpm@11.1.2+sha512.abc123..."
}
```

The suffix is a digest of the downloaded package manager. jup verifies a new download before adding it to the cache. On later runs, it just checks that jup's completed cache record matches the requested pin — it doesn't rehash every cached file on every command. Treat the cache as trusted executable state.

You don't need to calculate or type the digest yourself. Just run:

```sh
jup use pnpm@11
```

`pnpm@11` is a range, but `jup use` resolves it immediately and writes an exact version and digest.

Other selectors it accepts:

```sh
jup use pnpm@11.1.2   # exact version
jup use pnpm@^11.0.0  # semantic version range
jup use pnpm@latest   # registry tag
jup use pnpm          # current stable release
```

These are command-line selectors. A project declaration must include one, such as `"packageManager": "pnpm@11"` — a bare `"pnpm"` value in `package.json` is invalid.

Automatic selection skips prereleases such as `12.0.0-beta.1`. To use one, request it explicitly, provide a range that includes prereleases, or set `JUP_ENABLE_PRERELEASES=1`.

## Use `devEngines.packageManager`

Node also supports a structured declaration:

```json
{
  "devEngines": {
    "packageManager": {
      "name": "pnpm",
      "version": "11.x",
      "onFail": "error"
    }
  }
}
```

`version` can be exact or a semver range. `onFail` defaults to `error`: `error` stops on a mismatch, `warn` prints a warning and continues, and `ignore` continues silently. jup may still warn on a severely malformed declaration, since it can't reliably apply a policy it can't parse.

If this is the project's only declaration, `jup use` updates it in place to an exact version plus `integrity` — it doesn't add `packageManager`. When both forms exist, an exact `devEngines` version gets updated too, while a range stays as an additional constraint.

When both forms are present, `packageManager` supplies the active pin and `devEngines.packageManager` supplies an additional constraint, and jup checks that the two agree.

For example, this manifest pins one release while allowing any pnpm 11 release:

```json
{
  "packageManager": "pnpm@11.1.2+sha512.abc123...",
  "devEngines": {
    "packageManager": {
      "name": "pnpm",
      "version": "11.x",
      "onFail": "error"
    }
  }
}
```

When `jup up` updates the exact pin, it keeps the `11.x` constraint rather than replacing it with an exact version.

## Keep a range in `packageManager`

A manifest can contain a range directly:

```json
{
  "packageManager": "pnpm@^11.0.0"
}
```

A range can resolve differently as new releases appear. To make the result repeatable, jup records the selected release and digest in `.jup.lock`:

```json
{
  "version": 1,
  "resolutions": {
    "pnpm@^11.0.0": {
      "resolved": "11.1.2",
      "integrity": "sha512-..."
    }
  }
}
```

After writing the range, create or refresh its resolution locally with:

```sh
jup up
```

`jup up` keeps the range in `packageManager`, updates only its `.jup.lock` resolution, and runs the selected manager's install command. Review and commit both the dependency changes and `.jup.lock`. Future runs use the recorded release instead of asking the registry which version currently matches.

This is different from passing a range to `jup use`: `jup use pnpm@^11` resolves immediately and writes an exact pin. A range stays only when it's already in `packageManager` — for example, because it was written manually or by another tool.

When `CI` is set, normal commands freeze range resolutions by default, so a missing or stale entry fails instead of silently changing during the build. An explicit `jup up` is still allowed under CI's default, but `JUP_FROZEN_LOCKFILE=1` blocks even that. Set `JUP_FROZEN_LOCKFILE=0` only in a deliberate CI update job.

## Keep a registry tag in `packageManager`

A retained tag also uses `.jup.lock`:

```json
{
  "packageManager": "pnpm@latest"
}
```

`jup up` does **not** accept tags. To create the first resolution, run a normal manager command while connected and outside frozen mode:

```sh
jup pnpm --version
```

That resolves `latest`, caches and verifies the selected release, and records it under `pnpm@latest` in `.jup.lock`. Commit the file; later commands will keep using that recorded release even if the registry moves the tag.

To deliberately follow the tag again, remove its `pnpm@latest` entry from `.jup.lock` (or delete the file if it holds no other resolutions), then rerun the normal command and review the new lockfile. To follow a different channel, change the manifest to that tag — `pnpm@next`, say — and run the command to create its new entry.

If you no longer need the tag retained, this simpler command asks the registry what it currently means and writes the result as an exact pin:

```sh
jup use pnpm@latest
```

`jup use` also runs the selected manager's install command, so review its manifest, dependency, and lockfile changes. Exact `packageManager` pins don't need `.jup.lock`.

## Pin aube, Bun, Deno, or nub

aube, Bun, Deno, and nub are pinned like any other package manager:

```json
{
  "packageManager": "bun@1.4.0"
}
```

```sh
jup use aube@2.2.0
jup use bun@1.4.0
jup use deno@2.9.5
jup use nub@0.7.5
```

One difference shows up in the file: there's **no digest suffix**. These managers publish a different download for each supported host, so a single digest in `packageManager` wouldn't be portable. jup still verifies the artifact it selects for the current host before caching it — see [Download verification](./security).

With a range, `.jup.lock` records one digest per host:

```json
{
  "version": 1,
  "resolutions": {
    "bun@^1.4.0": {
      "resolved": "1.4.0",
      "integrity": {
        "linux-x64": "sha512-...",
        "darwin-arm64": "sha512-..."
      }
    }
  }
}
```

The version is shared, but each host needs its own digest entry. Under frozen mode, a new CI host can't add a missing entry, so run the range once on every target OS/architecture (and each Linux C-library variant) before freezing, and commit the combined `.jup.lock` — or deliberately refresh it in a trusted, unfrozen job. If a release has no build for the current host, jup reports that before it tries to download anything.

See [Getting started](./getting-started) to choose which optional shims to enable.

## Pin Node.js

Node is a runtime, not a package manager, so it's pinned in `devEngines.runtime`:

```sh
jup use node@22
```

```json
{
  "packageManager": "pnpm@11.1.2+sha512...",
  "devEngines": {
    "runtime": {
      "name": "node",
      "version": "22.23.2"
    }
  }
}
```

Node being a runtime rather than a package manager has three consequences, and they're the whole difference:

- **`packageManager` can't name it.** jup refuses a manifest that says `"packageManager": "node@22"` and points you at `devEngines.runtime` instead. `packageManager` is what jup enforces when you run the *wrong package manager* in a project, and a runtime isn't one.
- **The two fields don't constrain each other.** A project can pin pnpm and Node in the same manifest; each speaks for its own tool. Running `node` in a pnpm project is never a mismatch error, and running `pnpm` there is unaffected by the Node declaration.
- **`jup use node@…` writes the pin and stops.** Unlike `jup use pnpm@…`, there's no install command to run afterward.

Like the native package managers above, the pin carries no digest suffix, since Node also publishes a different download per host, and a range records one digest per host in `.jup.lock`.

Node's `node` shim is opt-in for the same reason Bun's and Deno's are — and more so, since `node` almost certainly already names something on your machine. `jup enable node` claims it deliberately.

### `.nvmrc`

If a project has no `devEngines.runtime`, jup falls back to the nearest `.nvmrc` — the same file, in the same directories, that `nvm` reads:

```sh
echo 22.23.2 > .nvmrc
jup node --version   # 22.23.2
```

jup only ever *reads* `.nvmrc`. `jup use node@…` writes `devEngines.runtime` and leaves `.nvmrc` alone, and a manifest that declares both is resolved by `devEngines.runtime` — so that field is how you override an `.nvmrc` you'd rather not delete.

jup understands versions and ranges: `22`, `v22`, `22.10`, `v22.23.2`, and `22.x` all work as written, and so do ranges nvm itself wouldn't accept, like `^22` or `>=20 <23`. Comments, blank lines, and `key=value` settings are skipped, exactly as nvm skips them.

Two nvm spellings resolve: `node` and `stable` both mean the newest release.

A range in an `.nvmrc` is recorded in a `.jup.lock` written next to that file, exactly as a range in `devEngines.runtime` would be — so in a monorepo the record lands beside the `.nvmrc` that declared it. An exact version needs no lockfile.

Everything else is an error rather than a guess:

- **`lts/*` and `lts/<codename>`.** The npm package jup uses to resolve Node versions only publishes LTS tags up to `v20-lts`, so there's nothing to answer `lts/*` with, and mapping codenames would mean shipping a table that goes stale every LTS line. Pin the line you mean instead — `22.x` — or declare it in `devEngines.runtime`.
- **`system`, `iojs`, `default`, and your own nvm aliases.** These name state in your `$NVM_DIR`, not a requirement of the project. `system` in particular asks for a Node that jup didn't install and can't verify.

jup doesn't use Node versions that nvm has already installed, and it doesn't install shell hooks or touch your profile. If both are on your `PATH`, whichever comes first wins — and since nvm re-prepends its directory on every shell start and every `nvm use`, that's usually nvm.

::note
Node publishes no musl build, so on Alpine and other musl Linux hosts jup reports that before downloading rather than caching a binary that can't start. `linux-armv7l` is likewise outside the set jup can name.
::

## Choose which manifest to edit

By default, commands that write a pin walk up from the current directory and stop at a manifest with `workspaces` or a directory containing `pnpm-workspace.yaml`. Commands that only read a pin can continue further upward, so nested packages can inherit the workspace pin. jup prints the exact path it changed.

Use `--here` to target `package.json` in the current directory:

```sh
jup use --here pnpm@11.1.2
jup up --here
```

If there's no manifest, `jup use --here` can create one. `jup up --here` can't create a manifest — it requires an existing, usable project pin in that directory.

Manifest lookup is broader when jup only needs to read a pin: a package without its own declaration can inherit one from a parent, which lets a single workspace pin apply to every package.

## Choose where to store the digest

By default, jup appends the digest to `packageManager`. This **suffix** style works with Corepack:

```json
{
  "packageManager": "yarn@4.14.1+sha512.abc123..."
}
```

Some tools accept only a plain version in `packageManager`. For those projects, use the **sidecar** style:

```sh
jup use --pin-style=sidecar yarn@4.14.1
```

It writes the digest separately:

```json
{
  "packageManager": "yarn@4.14.1",
  "devEngines": {
    "packageManager": {
      "name": "yarn",
      "version": "4.14.1",
      "integrity": "sha512-..."
    }
  }
}
```

jup verifies both styles. Use the default suffix for Corepack interoperability, unless another tool specifically requires plain version text. The sidecar is jup-specific — tools that ignore it just see the exact version.

Run `jup info` from any package to see which manifest and declaration jup selected.
