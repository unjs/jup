# Projects

> A project pin tells jup which package manager to run.

jup reads the pin from `package.json`, in either the `packageManager` field or Node's `devEngines.packageManager` object.

## Pin an exact version

The usual form is:

```json
{
  "packageManager": "npm@12.0.2+sha1.abc123..."
}
```

The suffix is a digest: a value used to check the downloaded package manager. jup verifies a new download before adding it to the cache. On later runs, jup checks its completed cache record against the requested pin. It does not hash every cached file again for every command. Treat the cache as trusted executable code.

A manager that ships a different file for each operating system and architecture is pinned without one, because a digest taken on your machine would fail on everyone else's. pnpm 12 and later is such a manager, as are aube, Bun, Deno, and nub:

```json
{
  "packageManager": "pnpm@12.1.2"
}
```

The version is still exact, and the download is still verified — against the registry's signature for your own system's file. See [Pin a manager with per-system builds](#pin-a-manager-with-per-system-builds).

You don't need to calculate or type a digest yourself. Just run:

```sh
jup use pnpm@12
```

`pnpm@12` is a range, but `jup use` resolves it immediately and writes an exact version, plus a digest where there is one to write.

Other selectors it accepts:

```sh
jup use pnpm@12.1.2   # exact version
jup use pnpm@^12.0.0  # semantic version range
jup use pnpm@latest   # registry tag
jup use pnpm          # current stable release
```

These are command-line selectors. A project declaration must include one, such as `"packageManager": "pnpm@12"` — a bare `"pnpm"` value in `package.json` is invalid.

Automatic selection skips prereleases such as `12.0.0-beta.1`. To use one, request it explicitly, provide a range that includes prereleases, or set `JUP_ENABLE_PRERELEASES=1`.

## Use `devEngines.packageManager`

Node also supports a structured declaration:

```json
{
  "devEngines": {
    "packageManager": {
      "name": "pnpm",
      "version": "12.x",
      "onFail": "error"
    }
  }
}
```

`version` can be exact or a semantic version (semver) range. `onFail` defaults to `error`. Use `error` to stop on a mismatch, `warn` to print a warning and continue, or `ignore` to continue silently. jup may still warn if the declaration is too malformed to read.

If this is the project's only declaration, `jup use` updates it in place to an exact version plus `integrity` — it doesn't add `packageManager`. When both forms exist, an exact `devEngines` version gets updated too, while a range stays as an additional constraint.

When both forms are present, `packageManager` is the active pin. `devEngines.packageManager` adds another constraint. jup checks that they agree.

For example, this manifest pins one release while allowing any pnpm 12 release:

```json
{
  "packageManager": "pnpm@12.1.2",
  "devEngines": {
    "packageManager": {
      "name": "pnpm",
      "version": "12.x",
      "onFail": "error"
    }
  }
}
```

When `jup up` updates the exact pin, it keeps the `12.x` constraint rather than replacing it with an exact version.

## Keep a range in `packageManager`

A manifest can contain a range directly:

```json
{
  "packageManager": "pnpm@^12.0.0"
}
```

A range may select a different version when new releases appear. To keep installs repeatable, record the selected release and digest in `jup.lock`:

```json
{
  "version": 1,
  "resolutions": {
    "pnpm@^12.0.0": {
      "resolved": "12.1.2",
      "integrity": "sha512-..."
    }
  }
}
```

Two commands write that file, and nothing else does. Set the range and record it in one step:

```sh
jup use pnpm@^12.0.0
```

This keeps the range in the field that declares the pin — `packageManager`, or `devEngines.packageManager` when there's no top-level field — records the release it selected in `jup.lock`, and prints both paths. Later, refresh the recorded release without touching the range:

```sh
jup up
```

Both commands then run the selected manager's install command. Review and commit the manifest, `jup.lock`, and the dependency changes. Future runs use the recorded release instead of asking the registry for the latest match.

Passing an exact version, a tag, or a bare name to `jup use` still writes an exact pin and no lockfile: `jup use pnpm@12.1.2`, `jup use pnpm@latest`, and `jup use pnpm` all resolve now and pin what they found.

### Runs don't change the recorded release

Running a package manager never writes or refreshes `jup.lock`. A build can't move a project to a release nobody reviewed, and `git status` stays clean.

When a range has no recorded resolution, jup resolves it and remembers the answer in `node_modules/.jup/jup.lock` for 24 hours. That file is a cache, not a record: it lives in a directory that's already ignored and already disposable — dot-prefixed, so npm doesn't read it as a stray package and delete it on the next install — it's only written when `node_modules` already exists, and if the registry can't be reached when the entry expires, the stale answer is used rather than failing the run — jup prints a `!` line naming the version it fell back to (mute it with `JUP_QUIET_ADVISORIES=1`) and doesn't extend the entry's 24 hours. Only unreachability counts: a disabled network, a minimum release age, an authentication failure (401 or 403), a version that doesn't exist (404), or a certificate that doesn't verify fails the run instead of quietly using the stale answer.

`JUP_FROZEN_LOCKFILE=1` makes `jup use <name>@<range>` and `jup up` fail instead of writing, and also refuses an exact `jup use` that would delete the recorded resolution of the range it replaces. Use it in a job that must not change the recorded release. It doesn't affect ordinary commands, which never wrote the file, and it doesn't affect the cache.

## Keep a registry tag in `packageManager`

A manifest can name a tag instead of a version:

```json
{
  "packageManager": "pnpm@latest"
}
```

A tag asks the registry what's current, so it isn't reproducible and jup doesn't record it. Each run uses the answer cached in `node_modules/.jup/jup.lock`, and asks the registry again once that entry is a day old. `jup up` doesn't accept tags.

For a reproducible project, replace the tag with what it currently means:

```sh
jup use pnpm@latest
```

This asks the registry now and writes the result as an exact pin. To keep updating within a line instead, write a range and record it with `jup use pnpm@^12.0.0`.

`jup use` also runs the selected manager's install command, so review its manifest, dependency, and lockfile changes. Exact `packageManager` pins don't need `jup.lock`.

## Pin a manager with per-system builds

aube, Bun, Deno, nub, and pnpm 12 and later are pinned like any other package manager:

```json
{
  "packageManager": "bun@1.4.0"
}
```

```sh
jup use aube@2.2.0
jup use bun@1.4.0
jup use deno@2.9.5
jup use nub@0.7.5
jup use pnpm@12.1.2
```

The pin has **no digest suffix**. These managers provide a different file for each supported system, so one digest in `packageManager` would not work everywhere. jup still verifies the file for the current system before caching it. See [Security](./security).

pnpm is the one that changes partway through its own history: releases up to 11 are JavaScript, one file for every system, and are pinned with a digest. From 12 pnpm is a native binary, published per system, and is pinned without one.

With a range, `jup.lock` records one digest per host:

```json
{
  "version": 1,
  "resolutions": {
    "bun@^1.4.0": {
      "resolved": "1.4.0",
      "integrity": {
        "linux-x64": "sha512-...",
        "darwin-arm64": "sha512-..."
      }
    }
  }
}
```

All systems share the version, but each host has its own digest entry, added when `jup use` or `jup up` runs on that host. A host with no entry still runs the recorded version: it verifies its download against the registry signature instead. To record every entry, run `jup use bun@^1.4.0` once on each target operating system and architecture, including each Linux C library variant, and commit the combined `jup.lock`. If a release has no build for the current host, jup reports this before downloading anything.

See [Start](./start) to choose which optional shims to enable.

## Pin Node.js

Node is a runtime, not a package manager, so it's pinned in `devEngines.runtime`:

```sh
jup use node@22
```

```json
{
  "packageManager": "pnpm@12.1.2",
  "devEngines": {
    "runtime": {
      "name": "node",
      "version": "22.23.2"
    }
  }
}
```

Because Node is a runtime rather than a package manager:

- **You can't name it in `packageManager`.** jup rejects `"packageManager": "node@22"` and tells you to use `devEngines.runtime`. The `packageManager` field only controls package managers.
- **The two fields are independent.** A project can pin pnpm and Node in the same manifest. Running `node` in a pnpm project does not cause a mismatch, and the Node pin does not affect `pnpm`.
- **`jup use node@…` only writes the pin.** Unlike `jup use pnpm@…`, it does not run an install command afterward.

Like the native package managers above, the pin carries no digest suffix, since Node also publishes a different download per host, and a range records one digest per host in `jup.lock`.

Node's `node` shim is opt-in for the same reason Bun's and Deno's are — and more so, since `node` almost certainly already names something on your machine. `jup enable node` claims it deliberately.

### `.nvmrc`

If a project has no `devEngines.runtime`, jup falls back to the nearest `.nvmrc` — the same file, in the same directories, that `nvm` reads:

```sh
echo 22.23.2 > .nvmrc
jup node --version   # 22.23.2
```

jup only *reads* `.nvmrc`; it never changes the file. `jup use node@…` writes `devEngines.runtime` instead. If a project has both settings, `devEngines.runtime` wins. Use it to override an `.nvmrc` that you want to keep.

jup understands versions and ranges: `22`, `v22`, `22.10`, `v22.23.2`, and `22.x` all work as written, and so do ranges nvm itself wouldn't accept, like `^22` or `>=20 <23`. Comments, blank lines, and `key=value` settings are skipped, exactly as nvm skips them.

Two nvm spellings resolve: `node` and `stable` both mean the newest release.

A range in an `.nvmrc` is resolved through the files next to that file, exactly as a range in `devEngines.runtime` would be — so in a monorepo jup reads the `jup.lock` beside the `.nvmrc` that declared the range, and caches its answer in the `node_modules/.jup` beside it. Since jup never writes `.nvmrc`, `jup use node@22` writes `devEngines.runtime`, and a `jup.lock` entry for an `.nvmrc` range is one you write yourself. An exact version needs no lockfile.

Everything else is an error rather than a guess:

- **`lts/*` and `lts/<codename>`.** The npm package jup uses to resolve Node versions only publishes LTS tags up to `v20-lts`, so there's nothing to answer `lts/*` with, and mapping codenames would mean shipping a table that goes stale every LTS line. Pin the line you mean instead — `22.x` — or declare it in `devEngines.runtime`.
- **`system`, `iojs`, `default`, and your own nvm aliases.** These name state in your `$NVM_DIR`, not a requirement of the project. `system` in particular asks for a Node that jup didn't install and can't verify.

jup doesn't use Node versions that nvm has already installed, and it doesn't install shell hooks or touch your profile. If both are on your `PATH`, whichever comes first wins — and since nvm re-prepends its directory on every shell start and every `nvm use`, that's usually nvm.

::note
Node publishes no musl build, so on Alpine and other musl Linux hosts jup reports that before downloading rather than caching a binary that can't start. `linux-armv7l` is likewise outside the set jup can name.
::

## Choose which manifest to edit

By default, commands that write a pin search upward from the current directory. They stop at a manifest with `workspaces` or a directory with `pnpm-workspace.yaml`. Commands that only read a pin can search farther upward, so nested packages can inherit the workspace pin. jup prints the exact path it changed.

Use `--here` to target `package.json` in the current directory:

```sh
jup use --here pnpm@12.1.2
jup up --here
```

If there's no manifest, `jup use --here` can create one. `jup up --here` can't create a manifest — it requires an existing, usable project pin in that directory.

Manifest lookup is broader when jup only needs to read a pin: a package without its own declaration can inherit one from a parent, which lets a single workspace pin apply to every package.

## Choose where to store the digest

By default, jup appends the digest to `packageManager`. This **suffix** style works with Corepack:

```json
{
  "packageManager": "yarn@4.14.1+sha512.abc123..."
}
```

Some tools accept only a plain version in `packageManager`. For those projects, use the **sidecar** style:

```sh
jup use --pin-style=sidecar yarn@4.14.1
```

It writes the digest separately:

```json
{
  "packageManager": "yarn@4.14.1",
  "devEngines": {
    "packageManager": {
      "name": "yarn",
      "version": "4.14.1",
      "integrity": "sha512-..."
    }
  }
}
```

jup verifies both styles. Use the default suffix for Corepack interoperability, unless another tool specifically requires plain version text. The sidecar is jup-specific — tools that ignore it just see the exact version.

Run `jup info` from any package to see which manifest and declaration jup selected.
