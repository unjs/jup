# Introduction

jup runs the exact package manager version your project needs, so developers, CI, and containers all end up using the same tool.

In an existing project with a valid `package.json`, set up your usual package-manager commands, then pin the version the project should use:

```sh
jup enable
cd my-project
jup use pnpm@11
pnpm install
```

`jup use` picks an exact release, verifies the download, caches it, and records it in the project's `package.json`. It then runs the selected manager's install command. Review the manifest, dependency, and lockfile changes before committing them; once committed, developers and CI can keep using the familiar command, always at the pinned version.

jup supports npm, pnpm, Yarn, aube, Bun, Deno, and nub, and it manages Node.js itself. npm, pnpm, Yarn, and aube get shims by default; Bun, Deno, nub, and Node are opt-in.

Node is a **runtime**, not a package manager, and that changes exactly one thing: a project declares it in `devEngines.runtime` instead of `packageManager`, and being pinned to some other package manager is never a reason jup refuses to run it. Everything else — resolution, verification, caching, execution — works the same way. A project with no `devEngines.runtime` falls back to its `.nvmrc`, so a checkout that has never heard of jup still gets the Node version it asks for.

::note
jup is not published to npm yet. Install it from source using the [getting started guide](./getting-started).
::
