# Introduction

jup runs the package manager version your project asks for. So developers, CI, and containers all use the same tool.

In an existing project with a valid `package.json`, set up normal package-manager commands, then choose the version the project should use:

```sh
jup enable
cd my-project
jup use pnpm@11
pnpm install
```

`jup use` chooses an exact release, verifies the download, caches it, and records it in that project's `package.json`. It then runs the selected manager's install command. Review the manifest, dependency, and lockfile changes before committing; after they are committed, developers and CI can use the familiar command with the same pinned manager version.

jup supports npm, pnpm, Yarn, aube, Bun, Deno, and nub, and it manages Node.js itself. npm, pnpm, Yarn, and aube get shims by default; Bun, Deno, nub, and Node are opt-in.

Node is a **runtime** rather than a package manager, which changes one thing: a project declares it in `devEngines.runtime` instead of `packageManager`, and standing in a project pinned to some other package manager is never a reason jup refuses to run it. Everything else—resolution, verification, caching, execution—is the same. A project with no `devEngines.runtime` is read from its `.nvmrc` instead, so a checkout that has never heard of jup still gets the Node version it asked for.

::note
jup is not published to npm yet. Install it from source using the [getting started guide](./getting-started).
::
