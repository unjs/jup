# Getting started

This guide installs jup, routes package-manager commands through it, and pins a pnpm release in a project. The same steps work with npm and Yarn.

## Requirements

You need:

- Node.js 22.18 or newer;
- Git;
- pnpm, either installed as a standalone command or temporarily available through Corepack; and
- a user-writable npm global installation directory on `PATH`.

jup isn't published to npm yet, so you'll build the current version from source.

## Install from source

Clone and build it with an existing standalone pnpm command:

```sh
git clone https://github.com/unjs/jup.git
cd jup
pnpm install
pnpm pack
```

If pnpm is only available through Corepack, keep it available until the archive is built:

```sh
git clone https://github.com/unjs/jup.git
cd jup
corepack enable pnpm
pnpm install
pnpm pack
```

`pnpm pack` names the archive after the version in `package.json`; `jup-0.0.0.tgz` below is just an example.

Before installing the archive, check the existing Corepack launcher and npm's global packages:

```sh
command -v corepack
npm prefix -g
npm ls -g corepack --depth=0
```

In PowerShell, use `Get-Command corepack` instead of `command -v corepack`. Then remove the old manager shims:

```sh
corepack disable
```

`corepack disable` does **not** remove the `corepack` launcher itself. The jup package also installs that command for compatibility, so finish the migration one of these ways:

- If `npm ls -g` shows a separately installed `corepack` package, run `npm uninstall -g corepack`, then `npm install -g ./jup-0.0.0.tgz`.
- If Corepack came bundled with Node.js, or you're not sure who owns it, compare `command -v corepack` with the global prefix you just printed. Once you've confirmed that path, deliberately replace the launcher:

  ```sh
  npm install -g --force ./jup-0.0.0.tgz
  ```

Don't use `--force` until you've checked which file it will replace. You shouldn't need administrator or root access as long as npm's global prefix is configured for your user. If a plain install works without replacing another launcher, prefer that.

To roll back, run `npm uninstall -g jup`, reinstall Corepack using its original installation method (or repair the Node.js installation that supplied it), then run `corepack enable pnpm`. The archive you packed is still there if you need to reinstall jup later.

Confirm the command is available:

```sh
jup --version
```

Once jup is released to npm, you'll be able to replace the source build with:

```sh
npm install -g jup
```

Don't use that command yet — it's not available until an official release is announced.

## Enable the shims

Run:

```sh
jup enable
```

This creates commands for `npm`, `npx`, `pnpm`, `pnpx`, `yarn`, `yarnpkg`, `aube`, `aubr`, and `aubx`. These small launcher files are called **shims**. They let jup inspect the current project before starting the package manager.

Bun, Deno, nub, and Node are supported but **not** shimmed by default, because each of those names also runs a file you hand it, and usually belongs to an installation you chose yourself. (aube only ever acts on a project, so it's shimmed by default along with the rest.) Ask for the others by name:

```sh
jup enable bun deno nub node
```

This adds `bun`, `bunx`, `deno`, `nub`, `nubx`, and `node`. A later `jup disable` with no arguments removes them along with everything else.

::warning
`jup enable node` puts jup's `node` ahead of your existing installation for every project on the machine. Enable it deliberately, and only if you want project-pinned Node everywhere. You can always run a pinned Node without a shim: `jup node@22 script.js`.
::

By default, jup installs shims in a user-owned directory: `$XDG_BIN_HOME` when set on non-macOS POSIX systems, otherwise `~/.local/bin` (including macOS), or `%LOCALAPPDATA%\jup\bin` on Windows. If that directory isn't on `PATH`, the command prints the line you need to add to your shell configuration. Open a new terminal after changing `PATH`. In an existing POSIX shell, you may also need:

```sh
hash -r
```

To install the shims somewhere else, give it a directory that's already on `PATH`:

```sh
jup enable --install-directory "$HOME/bin"
```

npm is included by default, which lets strict mode reject `npm install` when a project declares pnpm or Yarn. To leave your existing npm command untouched, exclude it:

```sh
jup enable --exclude npm
```

If jup reports a conflict, inspect the named path first:

```sh
command -v pnpm
jup info
```

jup leaves foreign command files alone by default. Use `--force` only when you deliberately want it to replace them:

```sh
jup enable --force
```

When jup displaces a command, it records what it replaced so `jup disable` can restore it later.

## Pin a package manager

Change to the project you want to configure, then run:

```sh
jup use pnpm@11
```

jup finds the newest matching pnpm 11 release, downloads and verifies it, and writes the exact version to `package.json`. The result looks like this (digest shortened for the example):

```json
{
  "packageManager": "pnpm@11.1.2+sha512.abc123..."
}
```

`use` then runs the selected manager's install command, so expect ordinary install output and possible dependency or lockfile changes. Review and commit everything intended, including the manifest.

## Run pnpm normally

With the shims enabled, use the command you already know:

```sh
pnpm install
```

Without shims, invoke the package manager through jup:

```sh
jup pnpm install
```

You can override the **version** for one command, but not the manager named by a strict project pin:

```sh
jup pnpm@11.22.0 --version
```

To switch this project from pnpm to Yarn, change its pin with `jup use yarn@<version>`.

## Check the result

Run the offline diagnostic report:

```sh
jup info
```

Use `jup info --json` for automation or a support attachment. Both forms stay offline, and both report every invalid project setting instead of stopping at the first one.

Check these sections:

- **Project** shows the manifest and pin jup found.
- **Resolution** shows the selected package manager version.
- **Store** shows whether that version is already cached.
- **Shims** shows where the launcher commands are installed and whether another command wins on `PATH`.
